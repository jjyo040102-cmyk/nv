# ActFlow: Nebius × NVIDIA 해커톤 분석과 제출 준비 평가

기준일: 2026-10-07, Asia/Seoul. 공식 웹페이지와 이 폴더의 소스·보고서·시연 자료를 대조했다. 공식 사실, 이번에 실행한 검증, 제안과 미검증 사항을 구분한다. 이 문서는 제품 개편을 검토하기 위한 분석이며, 기능 구현 완료 보고서가 아니다.

아래 코드·점수·실패 표는 변경 전 기준선이다. 이후 Nebius/NVIDIA 단일 추론, 2.0 실행본 승격, 명단의 구조·값 검증과 검증 후 확정을 적용했다. 최신 구현 및 검증은 [대회용 실행본 정리](2026-10-07-competition-cleanup.md)를 따른다. 변경 전 점수를 새 구현의 점수로 사용하지 않는다.

## 1. 판단

**ActFlow의 가장 좋은 방향은 ‘완료 근거를 제시하고 실패를 복구하는 지속 업무 Agent’다.** Policy Boundary, Verify, Rollback, Living Task는 좋은 기반이지만, 각각의 존재만으로 차별화하기는 어렵다. 사용자가 맡긴 일의 완료 조건을 구체적으로 정의하고, 실제 결과를 독립적으로 검사하며, 실패·복구·재개까지 같은 업무에서 보여주는 경험으로 묶어야 한다.

우선 목표는 네 개의 심사 항목에서 최고 수준의 증거를 준비하는 것이다. ‘100점’은 이 준비 수준의 목표이며, 심사위원 점수나 수상을 보장하는 표현으로 사용하지 않는다.

핵심 제안:

1. ActFlow 2.0 검토본을 기반 후보로 삼되, 검증을 통과하기 전 루트 앱을 덮어쓰지 않는다.
2. Nebius에서 NVIDIA Nemotron을 실제 업무 계획·실패 재계획에 사용한다.
3. 완료 조건을 Goal Contract로 저장하고, 독립적인 검증기를 실행한다.
4. 검증 전 결과는 임시 상태로 유지한다. 복구 가능한 변경은 기록에 따라 되돌린다.
5. 외부 전송은 별도의 실행 경계로 다룬다. 불명확한 전송 결과는 재발송하지 않는다.
6. 같은 Task가 답장과 시간 조건을 기다리고, 브라우저 종료와 worker 재시작 뒤에도 이어지는 것을 시연한다.

## 3. 트랙 선택

**추천: Best Apps and Agents.** 현재 제품의 중심은 업무 결과물, 승인, 조직 정책, 외부 회신이다. 한 사용자의 사생활·개인 스킬·개인 메모리보다 업무 흐름의 완성도를 증명하는 편이 현재 자산과 잘 맞는다.

Personal AI는 실제 상시 실행과 개인별 장기 기억이 핵심인 제품으로 완성되면 대안이다. Coding은 현재 업무 도구의 대상과 다르고, Physical AI는 현재 제품의 증거와 맞지 않는다. 공식 트랙 설명을 바탕으로 한 제품 적합성 판단이다. [대회 개요](https://nebiusglobalaihackathon.devpost.com/)

Serverless Endpoints/Jobs, NemoClaw/OpenShell/Hermes 등은 트랙 설명의 권장·예시 기술과 필수 요건을 구분해야 한다. 제출 직전 여러 프레임워크를 추가하는 것을 목표로 삼지 않는다. 현재 Next.js·SQLite 기반을 우선 사용하고, 상시 실행·배포에 필요한 경우에만 추가한다. [대회 개요](https://nebiusglobalaihackathon.devpost.com/)

## 4. 실제 심사 방식과 100점 환산

1차는 기본 작동성과 주제·필수 기술 적합성의 통과/실패 검사다. 통과작은 아래 네 항목에서 각각 1–5점, 동일 비중으로 평가된다. [공식 심사 안내](https://nebiusglobalaihackathon.devpost.com/updates/46204-here-s-how-judging-works)

내부 준비용 환산은 **100점 = 5 × 네 항목 점수 합계**로 둔다. 공식 발표가 100점제를 사용하는 것은 아니다. 동점 비교는 기술 구현부터 항목 순서대로 진행하므로 기술 사용과 실행 증거를 먼저 갖추는 것이 타당하다. [공식 규정](https://nebiusglobalaihackathon.devpost.com/rules)

| 공식 항목 | 보수적 자체 진단 | 5점 수준을 목표로 준비할 증거 |
|---|---:|---|
| Technological Implementation | 2/5 → 10/25 | 실 Nemotron 계획·재계획, 독립 검증, 복구 기록, 재시작·중복 방지, 재현 가능한 실행 |
| Design | 3/5 → 15/25 | 목표→진행→문제→승인→결과가 한 작업 화면에서 이어지고, 대기·실패의 이유가 명확함 |
| Potential Impact | 2/5 → 10/25 | 특정 업무 담당자, 실제 관찰한 불편, 수동 대비 시간·수정·확인 부담 측정 |
| Quality of the Idea | 3/5 → 15/25 | 기존 승인·메모리 기능과 구별되는 완료 조건·검증·보상·지속 업무의 통합 데모 |
| 합계 | **50/100, 자체 준비 진단** | 네 항목 모두의 근거를 채우는 것을 목표로 함 |

이 점수는 공식 심사 결과 예측이 아니다. 소스 검토·로컬 테스트만 있고 실제 모델, 외부 커넥터, 사용자 평가가 부족한 상태를 보수적으로 표시한 것이다. **필수 기술 사용 증거가 없는 현재 상태는 1차 통과 준비 미완료**이며, 기능 점수 합계로 이를 상쇄할 수 없다.

심사위원 명단에는 NVIDIA 소프트웨어·AI 엔지니어, Nebius 제품·ML·개발자 관계 담당자가 포함돼 있다. 개인의 취향을 추측하기보다, 엔지니어에게는 상태·복구의 증거, 제품 담당자에게는 사용자 가치, 플랫폼 담당자에게는 실사용·피드백을 제공하는 구성이 유리하다는 판단이다. [대회 개요](https://nebiusglobalaihackathon.devpost.com/)

2.0의 세 테스트 실패:

- policy.test.ts: external.email.send의 기대값 CONFIRM과 실제값 HUMAN_ONLY가 불일치한다. 보안 수준을 낮춰 통과시키지 말고, 현재 전송 사양·정책 맥락과 테스트를 맞춰야 한다.
- task-dashboard.test.tsx: ‘자동 이어하기 대기’가 상태 요약과 작업 카드에 함께 나와 단일 텍스트 조회가 실패한다.
- task-workspace.test.tsx: EMAIL이 이벤트와 기억 출처에 함께 나와 단일 텍스트 조회가 실패한다.

뒤의 두 실패는 관찰된 조회 모호성이다. 이것만으로 화면의 기능이 고장났다고 단정하지 않는다. 수정한다면 역할·영역에 기반한 조회로 사용자 경험을 검증해야 한다. 첫 실패도 사양 불일치부터 판단한다.

### 검증 반례의 내용

‘메모 / 잘못된 값’ 두 열만 있고 ‘김민지 이준호’가 한 메모 셀에 들어 있는 XLSX를 만들었다. 실제 명단의 필수 열인 사번·이름·부서·직책·교육 대상이 없고, 두 직원의 개별 행도 없다. 그런데 requiredTexts로 두 이름을 넣으면 양쪽 검증기 모두 통과한다.

근거 파일: [실제 검사 JSON](../../data/runtime/hackathon-audit-2026-10-07/semantic-verification-probe.json), [반례 XLSX](../../data/runtime/hackathon-audit-2026-10-07/wrong-roster.xlsx). JSON에는 SHA-256과 두 버전의 결과가 남아 있다. 이것은 한 종류의 검증 허점을 재현한 것이며 전체 오류율 측정은 아니다.

| Rollback | 거절 시 임시 파일 삭제 | 임시 삭제·복구 경로 유지 | 실행 실패 시 보상 기록·역순 복구·복구 후 독립 확인 |
| 외부 메일 | sent:false 시뮬레이션 | outbox·전송 인터페이스·SIMULATED receipt | 최소 한 개 실 transport와 원격 결과 재조회 |
| Living Task | 단일 workflow, 재시작 자동 복구 없음 | Task/Memory/Wake/lease/recovery 있음 | 실프로세스 중단·재시작과 이벤트 재처리 E2E |
| 상시 실행 | 브라우저가 API 실행을 시작 | Node 서버 timer·instrumentation | 브라우저 없는 worker 실행·건강 상태·명시적 실행 한계 |
| 공개 평가 | 로컬 데모 역할 인증 | 로컬 데모 역할 인증 | 무료 test build 또는 제한된 공개 데모 접근 |

소스 근거: [루트 엔진](../../lib/workflow/engine.ts), [루트 검증기](../../lib/workflow/verifier.ts), [2.0 엔진](../../data/runtime/review-ActFlow-2.0-Stabilized-RC/ActFlow-2.0-Stabilized/lib/workflow/engine.ts), [2.0 Wake](../../data/runtime/review-ActFlow-2.0-Stabilized-RC/ActFlow-2.0-Stabilized/lib/events/wake-engine.ts), [2.0 outbox](../../data/runtime/review-ActFlow-2.0-Stabilized-RC/ActFlow-2.0-Stabilized/lib/email/outbox.ts).

2.0에는 이벤트 중복 제거, 작업 lease, 승인 대기 중 이벤트 보관, 성공 receipt 복원, 불확실한 SENDING→UNKNOWN 처리가 이미 있다. 새 기능처럼 재구현하지 않고 이 경로를 실제 환경에서 확인하는 것이 우선이다.

## 8. 제안한 방향을 그대로 사용하지 않는 이유

**‘일반 Agent에는 승인·기억이 없다’는 주장은 피한다.** Microsoft Copilot Studio의 다단계 승인 기능은 사람·AI·조건을 결합한다. 해당 고급 기능은 문서상 preview다. [Microsoft 공식 문서](https://learn.microsoft.com/en-us/microsoft-copilot-studio/flows-advanced-approvals)

LangGraph는 checkpoint와 store로 작업 상태·사용자 선호·중단 이후 재개를 다룬다. 따라서 ‘대화 이후에도 기억한다’만으로 새로운 기술이라고 주장할 수 없다. [LangGraph 공식 문서](https://docs.langchain.com/oss/python/langgraph/persistence)

NVIDIA NemoClaw/OpenShell에도 기본 차단과 미등록 네트워크 요청의 운영자 승인 경계가 있다. ActFlow는 이보다 업무의 수신자·파일·목표 조건까지 다루는 제품 계층에서 가치를 증명해야 한다. [NVIDIA 공식 문서](https://docs.nvidia.com/nemoclaw/latest/user-guide/openclaw/reference/network-policies)

ActFlow의 차이는 다음을 **한 업무에서 검사 가능하게 통합한 경험**으로 제시한다:

- 모델이 제안한 행동과 실제 허용된 행동을 구분한다.
- 도구 성공과 사용자가 요청한 목표 달성을 구분한다.
- 무엇을 바꿨고 무엇을 복원했는지 보여준다.
- 나중에 도착한 사건에도 같은 목표·정책·근거를 유지한다.
- 안전한 정상 작업을 실제 완료하면서 위험·오류를 차단한다.

이는 경쟁 제품 전체에 해당 기능이 없다는 사실 주장이 아니라, ActFlow가 집중할 제품 가치의 정의다.

## 9. 100점 수준으로 준비할 제품 범위

추천 첫 사용자는 **소규모 팀의 운영·교육 담당자**다. 현재 직원 명단·비용 승인·DOCX/XLSX 생성이라는 자산을 바로 사용할 수 있다. 장기 시장은 반복적인 외부 자료 제출·온보딩 업무지만, 이번 시연은 교육 신청 회신 하나로 좁힌다.

주력 목표: **‘교육 신청 자료를 정확히 만들고, 승인된 상대에게 제출한 뒤 접수 상태를 확인해줘.’** 비용 검토는 승인 절차이며 실제 지급을 뜻하지 않는다.

강한 데모는 편리함만 보여주지 않는다. 의도적으로 잘못된 파일을 생성했는데 도구가 성공을 반환한 상황에서, ActFlow가 결과를 거절하고 임시 변경을 복구한 뒤 실제 Nemotron이 오류 근거를 읽어 재계획하는 장면을 보여준다. 이어서 정확한 상대에 대한 승인·실전송·대기·재시작·Wake를 증명한다.

문서 생성 16.53ms 개선은 기존 고정 Demo 측정일 뿐이며 주요 가치로 쓰지 않는다. ‘확인 비용과 잘못된 완료를 줄이고, 중단돼도 일을 잃지 않는가’를 측정해야 한다.

## 10. 우선순위와 일정 제안

아래는 검토용 제출 일정이다. 실제 착수 시 팀 규모·크레딧·실메일 계정 상황에 맞춰 조정한다. 기본 가정은 기존 코드 재사용과 1개 시나리오 완성이다.

## 11. 제외할 일과 사업성 검증

이번 범위에서는 계약 서명·결제·ERP·범용 PC 조작·커넥터 마켓·모델 학습·여러 로컬 GPU 배포를 추가하지 않는다. Qwen 설치와 여러 제공자 설정은 고급 설정으로 남기고, 해커톤 시연은 Nebius/NVIDIA 경로를 기본으로 한다.

사업성은 아직 검증되지 않았다. 운영 담당자 3–5명에게 실제로 반복되는 제출 업무, 확인 시간, 실수 복구 비용, 허용할 자동 실행 범위를 관찰한다. 판매 규모나 절감률을 가정해서 결과처럼 쓰지 않는다. 기업용 확장은 운영 인증·조직 권한·다중 사용자·정보 처리 권한이 갖춰진 이후다.
